5-minute quickstart

1 Register audit codes — once, at startup

python
import rivet
from rivet.codes import register, Meta, Severity, RetentionClass

register("user", [
    ("USER_CREATED", Meta(
        id="USER_CREATED", domain="user", category="account",
        action="create", severity=Severity.INFO,
        description="New user account created", emitter="auth-service",
        retention_class=RetentionClass.LONG,
    )),
    ("USER_DELETED", Meta(
        id="USER_DELETED", domain="user", category="account",
        action="delete", severity=Severity.WARN,
        description="User account permanently deleted", emitter="auth-service",
        retention_class=RetentionClass.LONG,
    )),
])

2 Init — reads env vars; RIVET_AUDIT_DSN required

.env
RIVET_AUDIT_DSN=sqlite:///./audit.db   # or postgres://...
python
rivet.init(service_id="auth-service", node_id="host-01")
# reads RIVET_AUDIT_DSN; raises RuntimeError if unset.
# Audit rows go to durable storage — no silent in-memory fallback.

3 Emit anywhere

python
rivet.emit(code="USER_CREATED", target="u-42",
           actor="admin", detail={"email": "alice@example.com"})

rivet.log.info("signup_complete", user_id="u-42")

Production: env-var driven

.env
RIVET_SERVICE_ID=auth-service
RIVET_NODE_ID=host-01
RIVET_AUDIT_DSN=postgres://user:pw@db:5432/appdb
python
rivet.init()   # reads everything from env — same emit() call

Debugging a real incident

Scenario: A pipeline config change was applied at 14:32. By 14:33 the MQTT broker shows message loss.

Without rivet

  1. docker logs gateway | grep 14:32 — hundreds of lines, no actor info
  2. docker logs pipeline-engine | grep 14:32 — different format, different timestamps
  3. Cross-reference manually — which request caused which effect? Unknown.
  4. Ask on Slack "who changed the config?" — 20-minute delay

With rivet — one query, 30 seconds

bash
curl "/api/v1/logs/audit?since=2026-04-24T14:30:00Z&until=2026-04-24T14:35:00Z"
response — 3 rows, same request_id threads all of them
[
  { "timestamp": "14:32:11Z", "code": "CONFIG_NODE_UPDATED",
    "actor": "praveen", "actor_kind": "human", "method": "http",
    "target": "pipelines/modbus-01/connection/url",
    "request_id": "req-9f8e7d6c",
    "detail": {"old": "modbus://10.0.1.10", "new": "modbus://10.0.2.10"} },

  { "timestamp": "14:32:12Z", "code": "CONNECTOR_DISCONNECTED",
    "actor": "system", "method": "mqtt", "target": "modbus://10.0.1.10",
    "request_id": "req-9f8e7d6c" },

  { "timestamp": "14:32:14Z", "code": "CONNECTOR_CONNECTED",
    "actor": "system", "method": "mqtt", "target": "modbus://10.0.2.10",
    "request_id": "req-9f8e7d6c" }
]

Same request_id threads the HTTP config change, MQTT disconnect, and reconnect — across two services and two transports. 30 seconds vs 20 minutes.

The 7 anchors

5 Ws + H + CORRELATION — enforced at the type level. Caller supplies only code, target, and optional detail. Everything else auto-fills.

AnchorFieldsAuto-filled?
WHO actor, actor_kindfrom ctx / caller
WHAT code, actioncode from caller; action from Meta
WHEN timestamp, monotonic_seqauto
WHERE source_node_id, service_id, tenant_idauto from rivet.init()
WHOM target, category, domaintarget from caller; rest from Meta
HOW method ∈ {http, mqtt, cli, scheduler, ui, agent_tool}auto from shim / caller
CORRELATION request_idfrom context; minted if absent

WHY lives in detail.reason (free text). A policy plugin can enforce it on mutation codes.

Three streams

StreamStorageEndpointPersistent?
syslog In-memory ring (10k lines) /logs/sys No — ring only
API logRing + opt-in SQL /logs/api Opt-in via RIVET_API_DSN
audit SQL rivet_audit/logs/auditYes — per-code TTL

All three carry request_id. A ?request_id=<id> query returns rows from all services that carried it — the Jaeger alternative for audit + correlation.

Schema

rivet owns one SQLite file (rivet.db). Your product owns its own DB. They share a request_id join key — they never share a file.

storage layout
{DATA_DIR}/rivet.db       ← rivet owns this (created by rivet.init())
  └── rivet_audit          ← one row per emit(); TTL-swept by rivet
  └── rivet_api_log        ← opt-in; one row per HTTP request

{DATA_DIR}/your-app.db   ← your product owns this
  ├── ...your tables...
  └── audit_replay         ← YOUR table; soft-ref to rivet_audit.id
                             holds replay_payload for recovery

rivet_audit columns

ColumnTypeNotes
idTEXT PKevt-<20-hex>
codeTEXTe.g. USER_CREATED
actor / actor_kindTEXTWHO anchor
target / category / domainTEXTWHOM anchor — adopter-defined strings
service_id / source_node_id / tenant_idTEXTWHERE anchor — from init()
methodTEXTHOW anchor
request_idTEXTCORRELATION — join key across streams
timestamp / monotonic_seqTEXT / INTWHEN anchor
detailJSONAdopter-owned free blob; secrets redacted

rivet creates rivet_audit via idempotent CREATE TABLE IF NOT EXISTS on init(). Your product creates audit_replay via its own migrations. Never mix them in the same file.

API mounting

rivet's reader is a mountable router — not a standalone service. Wire it in like any sub-router under whatever prefix you choose.

Python (FastAPI)

python
import rivet
from fastapi import FastAPI
from rivet.shim.http import RequestIDMiddleware

rivet.init()
app = FastAPI()
app.add_middleware(RequestIDMiddleware)       # mints / honours X-Request-ID
app.include_router(rivet.reader.router(), prefix="/api/v1/logs")

# GET /api/v1/logs/sys
# GET /api/v1/logs/api
# GET /api/v1/logs/audit?code=USER_CREATED&actor=admin

Go (chi)

go
import (
    rivet    "github.com/nerdapplabs/rivet-go/rivet"
    httpshim "github.com/nerdapplabs/rivet-go/rivet/shim/http"
)

rivet.Init(rivet.Config{})
r := chi.NewRouter()
r.Use(httpshim.RequestID)
r.Mount("/api/v1/logs", rivet.NewReader())
// GET /api/v1/logs/sys  |  /api  |  /audit

rivet vs your own DB

QuestionAnswer
Who creates rivet_audit?rivet's init() — idempotent
Who creates audit_replay?Your product's schema migration
Can I query rivet's store directly?rivet._get_audit_store().query(…) or GET /logs/audit
Can rivet query audit_replay?No — it doesn't know about it
Where does syslog live?In-memory ring only — no SQL table
How do they join?Via request_id — pass the same id in both contexts

Security model

Where rivet's responsibility starts and stops depends on whose database holds the audit rows. Two storage modes, four zones.

Responsibility split

Zone Mode 1 — your DB Mode 2 — rivet's DB
At write
redaction · schema · registry integrity · SQL safety		 rivet rivet
At rest
file perms · encryption · backup · retention sweep		 You. Perimeter is your DB's existing security — RBAC, KMS, network isolation. rivet ships safe defaults; encryption-at-rest hooks documented.
At read
authn · authz · CORS · rate limit		 You. Mount the reader behind your existing auth (FastAPI Depends, gateway, session middleware). rivet ships X-Rivet-Key + per-app key registry. Off by default; opt in.
Distribution
signed releases · SBOM · CVE disclosure · vuln scanning		 rivet rivet

One sentence: rivet is responsible for the row's integrity from emit to insert, and for any surface rivet itself exposes — but never for the security of storage you brought.

Mode 1 — wire your existing auth

The reader is a FastAPI router. Mount it like any other route, behind whatever auth your app already runs.

python
from fastapi import Depends
from your_app.auth import require_audit_read   # your existing dependency

app.include_router(
    rivet.reader.router(),
    prefix="/api/v1/logs",
    dependencies=[Depends(require_audit_read)],   # ← your check, your rules
)

rivet's reader doesn't add its own check here. Two auth layers fight each other; one well-placed layer is the point.

Mode 2 — bundled key system planned

When rivet owns the DB, the reader is the only query path — and there's no adopter-side auth surface to delegate to. So rivet ships keys.

ConceptDetail
HeaderX-Rivet-Key: <key> — server-to-server, namespaced, never collides with your Authorization
Storagereader_keys table; values stored as sha256 hash, plaintext shown once at creation
Lifecyclerivet key create / list / revoke / rotate — direct DSN access, no HTTP bootstrap problem
Scopeper-stream (audit, sys, api); cloud: per-tenant + per-site
Audit-of-the-audit-logevery READER_QUERY and READER_AUTH_BAD emits an audit row with actor_kind=app, actor=key.name
Bundled toolsrivet tui + rivet tail honour RIVET_READER_KEY automatically

Why X-Rivet-Key, not Authorization: Bearer

The reader is a server-to-server hop, never user-bearing. Custom-namespaced header avoids four real problems:

  • No collision. Mode 1 already carries Authorization: Bearer <user_jwt> for the adopter's user auth. Two different things in one header is a layering bug waiting to happen.
  • Intent is explicit. Anyone reading the wire / middleware logs sees the rivet boundary at a glance — machine credential, not user.
  • Logs / redaction. Add X-Rivet-Key to your proxy's redact-list once and forget. The custom name makes the redact intent obvious.
  • CORS. Goes into a clean Access-Control-Allow-Headers allowlist without fighting Authorization semantics.

Convention match: AWS uses signed headers, GCP uses X-Goog-Api-Key, Cloudflare uses X-Auth-Key. Same family.

Two-tier flow

Mount the reader inside an app that also serves end-users → two independent guards on independent hops:

wire
end user  ──Authorization: Bearer <user_jwt>──>  your app
                                                  │
                                  (your auth verifies user)
                                  (your ACL: can this user read audit?)
                                                  │
                                                  ▼
your app  ──X-Rivet-Key: <key>──>  rivet reader   (in-process or sidecar)
                                                  │
                                  (rivet verifies key + scope)
                                  (emits READER_QUERY audit row)
                                                  │
                                                  ▼
                                                data

Each layer logs its own audit row. Each can be revoked independently. Neither pretends to do the other's job.

Reserved headers

HeaderPurpose
X-Rivet-Request-IdCorrelation id bundled
X-Rivet-Key API key for the bundled reader (Mode 2) planned
X-Rivet-Scope Optional — multi-scope keys declare which scope they're using planned

What stays out of scope

  • TLS termination — your reverse proxy / load balancer.
  • Network ACLs — your VPC / firewall / k8s NetworkPolicy.
  • Key distribution — your secret manager (Vault, k8s Secret, AWS SSM).
  • DB encryption at rest — Mode 1: your DB. Mode 2: OS-level on the SQLite file, or Postgres TDE.

Operational FAQ

What is the latency overhead?

~0.1–0.5 ms per emit() with SQLite WAL (synchronous). ~1–5 ms with Postgres. rivet.log.* is ring + stdout only — sub-millisecond, no SQL write. High-volume codes (>100/sec): set high_volume=True in Meta to skip the SQL insert.

What is the memory footprint?

Two rings per service: syslog 10k × ~500 B ≈ 5 MB + API log 10k × ~300 B ≈ 3 MB = ~8 MB total at full occupancy. Tune with RIVET_SYS_RING_SIZE and RIVET_API_RING_SIZE.

Does SQLite contend under concurrent writes?

WAL mode allows concurrent readers + one writer. For typical audit volumes (config mutations, lifecycle events) this is not a concern. If you see contention, mark hot codes high_volume=True or switch to Postgres.

Does rivet add a thread or process?

No. In-process library. The ring buffer uses a mutex (channel in Go). No goroutines, no threads, no sidecar.

What happens if the DB is unavailable?

  • The row is written to stdout regardless — Docker / journald captures it.
  • The SQL insert fails silently in the request path; the row is not lost.
  • For guaranteed durable SQL persistence, use the outbox variant with a retry queue (planned).

Does rivet work in air-gapped environments?

Yes. Stdout is the primary transport — no network required. SQLite works fully offline. Rows drain upstream when connectivity resumes.

PII — three mechanisms

1. Redaction at emit time — keys matching known patterns (api_key, password, token, authorization) have values replaced with *** before writing anywhere.

python
rivet.emit("USER_CREATED", target="u-42",
           detail={"email": "alice@acme.com", "api_key": "sk-abc123"})
# stored: {"email": "alice@acme.com", "api_key": "***"}

rivet.init(..., extra_redact_keys=["ssn", "credit_card", "dob"])

2. PII class flag — forces retention to short regardless of declared class:

python
Meta(..., pii_in_detail=True)   # overrides → retention_class: short (30 days)

3. TTL sweep — rows beyond their class are deleted on schedule. For GDPR right-to-erasure: delete rows by actor or target, then let TTL sweep clean up the rest.

Code evolution + compatibility

Renaming a code

python
# v1
register("user", [("USR_CREATED", Meta(...))])

# v2 — rename; keep old emittable for one release
register("user", [
    ("USER_CREATED", Meta(...)),
    ("USR_CREATED",  Meta(..., declared_unused=True)),  # old rows still readable
])

Schema contract

The 7 anchor columns are stable — never change type. detail is yours to evolve freely. Adding keys is always compatible; changing a key's type is a breaking change.

stable columns — rivet's public contract
id, origin_id, monotonic_seq, timestamp, code, action, severity,
service_id, source_node_id, tenant_id,
actor, actor_kind, target, category, domain, method, request_id

detail  ← free JSON — you own its schema

OTel / trace_id bridge

Pass your OTel trace_id as rivet's request_id — they become the same id. A future transport/otlp plugin will export audit rows as OTel LogRecord entries, letting existing Grafana/Jaeger stacks query rivet rows.

python
from opentelemetry import trace
span = trace.get_current_span()
ctx = rivet.context.set_request_id(
    format(span.get_span_context().trace_id, '032x')
)
