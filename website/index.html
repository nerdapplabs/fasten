One env var picks the engine.
Same code, SQLite to Postgres.

Audit rows always go to durable storage — rivet never silently uses in-memory. Set RIVET_AUDIT_DSN once; swap engines by changing one variable. Secrets stay in .env / k8s Secret / vault — never in code.

audit model

5 Ws + H — enforced at the type level.

The classical audit vocabulary. No string-soup attributes. Auditors already think in this frame.

WHOactor · actor_kindadmin · scheduler · system · agent
WHATcode · actionPIPELINE_DEPLOYED · TOOL_CALLED
WHENtimestamp · seqUTC ms · per-node monotonic
WHEREnode · service · tenantmulti-tenant / multi-site filter
WHOMtarget · category · domainthe object of the action
HOWmethodhttp · mqtt · cli · scheduler · ui · agent_tool
+ CORRELATIONrequest_idthreads every stream, every transport

retention · pii · api log

Per-code TTL. PII-aware. API log opt-in.
Tune without code changes.

Not every audit row deserves the same retention.

  • Compliance-core events — stay for years.
  • High-volume trigger events — sweep early.
  • Anything tagged pii_in_detail — forced minimisation.
  • API log — opt-in persistence; default is ring-buffer only.

Per-code retention class

audit

Every code declares a class: short, medium, long. The retention sweep deletes expired rows — on edges, never before they've replicated to the aggregator. 

# defaults, per class
short    30 days    # e.g., TRIGGER_FIRED, BATCH_PROCESSED
medium   180 days   # e.g., CONFIG_UPDATED, JOB_COMPLETED
long     3 years    # e.g., AUTH_LOGIN, PAYMENT_COMPLETED
# override via env — no code change
RIVET_AUDIT_RETENTION_CLASS_LONG=2555          # 7y (regulated)
RIVET_AUDIT_RETENTION_OVERRIDE="long=7y,medium=1y"
RIVET_RETENTION_SWEEP_INTERVAL=6h

PII minimisation + API log persistence

opt-in

Codes declared pii_in_detail: true force the short class regardless — GDPR-style "shortest safe retention" by default. API log rows go ring-buffer + stdout by default; persist them via RIVET_API_DSN for HIPAA PHI access, GDPR access trails, SOC2 HTTP audit. 

# .env — opt into persistent API log
RIVET_API_DSN=postgres://user:pw@db/app?table=api_log
RIVET_API_RETENTION_DAYS=180                   # HIPAA-friendly
# code declaration — retention + PII class on the code
register("user", [
  ("AUTH_LOGIN",  Meta(..., retention_class="long")),
  ("AUTH_FAILED", Meta(..., retention_class="long",
                              pii_in_detail=True)),
])

Retention applies to all three streams. Syslog + API log also have ring-buffer size caps (RIVET_SYS_RING_SIZE, RIVET_API_RING_SIZE); docker log-driver rotation handles on-disk stdout size.

advanced · optional

Beyond HTTP — cross-transport correlation.

HTTP is table stakes. rivet's wedge is the transports HTTP-only tools skip:

  • MQTT — industrial / IoT / pub-sub.
  • scheduler — autonomous, cron-fired jobs.
  • deploy pipeline — multi-service handoffs.

Each is an opt-in shim. Most adopters never need these.

MQTT round-trip

industrial · IoT

mqtt_shim.publish() auto-injects _req into the payload. The subscriber's mqtt_shim.handler() reads it back into ctx. Every log the subscriber emits during handling carries the same id. 

# publisher (HTTP handler — user sets a new setpoint)
await rivet.shim.mqtt.publish(
    client, f"devices/{device_id}/setpoint",
    {"target_temp_c": 22.5},
)
# shim injects _req = current_request_id() into payload
# subscriber (device firmware, any language)
@mqtt_shim.handler("devices/+/setpoint")
async def on_setpoint(msg, ctx):
    # ctx.request_id == original HTTP caller's id
    rivet.log.info("setpoint_received")
    rivet.emit(code="DEVICE_SETPOINT_UPDATED", ...)
# operator — one query stitches both services
$ rivet tail --stream audit --request-id abc
SETPOINT_REQUESTED       api-server  actor=admin   target=dev-42
DEVICE_SETPOINT_UPDATED  device-42   actor=system  # same id ✓

Scheduler shim

autonomous jobs

Cron-fired jobs have no external caller. Without a shim, every scheduled audit row has null or freshly-minted request_id. The scheduler shim mints scheduler-<run_id> at job start, stashes it in ctx. 

@scheduler.cron("0 */6 * * *")
@rivet.shim.scheduler.instrument
async def nightly_cleanup():
    # request_id = "scheduler-a1b2c3d4"
    rivet.emit(code="RETENTION_SWEEP_RAN", ...)
    rivet.log.info("cleanup_done")
# all rows for this run share the same id

Deploy pipeline

multi-service

X-Deploy-ID piggybacks on X-Request-ID so a deploy that fans out across orchestrator → relay → target threads one causal chain. Generic shim — works for any multi-service handoff (CI/CD, config rollout, multi-region replication).

Custom transport (gRPC, NATS, AMQP, Kafka)? Write a 10-line shim following the same read-id-from-wire / set-ctx / call-downstream pattern.

origin

Why we built this.

  1. 01

    The setup.

    An industrial edge platform — many services, many languages, all on MQTT.

    • Gateway · Python
    • Fleet manager · Go
    • Sync relay · Go
    • Connectors · Node + Go
  2. 02

    The recurring question.

    "This event fired at 14:02 — show me what happened next across all these services."

    Answer, every week: grep + timestamp math + cursing.

  3. 03

    What we tried — in the order we tried it.

    1. Our log libraries. structlog and slog format beautifully — but they're loggers, not auditors. No typed shape, no correlation contract. Both still ship in our stack; rivet sits alongside.
    2. OpenTelemetry. Traces threaded HTTP cleanly. The moment we crossed into MQTT, scheduler-fired jobs, or a deploy pipeline, we were propagating context by hand — and OTel still wouldn't commit to a typed audit row.
    3. Loki for centralisation. Aggregated lines across the fleet — exactly what it's built for. But the body was free-text and the labels were whatever you remembered to attach. The audit join came back to grep.
    4. Our own audit tables. Worked. Then drifted. Three services, three shapes, no shared retention contract — the classic in-house path.
    5. LangSmith — for the AI-agent path. Tool calls feel audit-shaped, so we looked. Beautifully built — and locked to LangChain we weren't using.
    6. Buying it. Splunk cost more than the rest of our infrastructure combined. Enterprise compliance tools were opaque black boxes — we couldn't audit the auditor.

    None of these, alone or stitched, covered the gap: typed audit threaded across every transport, with one correlation key.

  4. 04

    So we built the missing piece.

    • 5 Ws + H enforced at the type level.
    • One request_id threaded across every transport.
    • A storage contract portable across five languages.

    Open-source because:

    • Regulated buyers won't adopt a closed audit library.
    • Our moat is the paid data plane — rivet Cloud.
    • The community writes adapters we'd never ship ourselves.

faq

Common questions.

Do I have to replace my existing logger (structlog / slog / pino)?

No. rivet sits alongside your existing logger. Keep using structlog / slog / pino / winston for free-form application logs; use rivet.emit() for typed audit events. rivet.log.* is optional — it mirrors the idioms of each language (kwargs in Python, positional pairs in Go, object-first in pino) if you want one logger across both streams.

How is this different from OpenTelemetry?

OTel is deliberately untyped — it unifies logs / metrics / traces at the protocol layer but leaves semantics to you. rivet adds the typed 6-anchor audit shape OTel doesn't commit to, and ships shims for transports (MQTT, scheduler, deploy pipeline) where OTel's ecosystem is thin. request_id ↔ trace_id, so they coexist natively via OTel export.

Do I need rivet Cloud to use the SDK?

No. The SDK is Apache-2.0 and complete on its own — emit, store, query, CLI, shims, retention, PII minimisation. rivet Cloud is the commercial fleet-aggregation + compliance-report layer. Most adopters never need it; single-node and small-fleet deployments use the SDK alone.

Is there a daemon, sidecar, or agent to run?

No. rivet is a library you import; it runs in your process. No rivetd, no sidecar, no required hosted service. The bundled CLI (rivet dump / tail / doctor) is a debug tool, not a background process.

Is this production-ready?

Alpha / pre-v1. The reference implementation is still being built inside our own platform. API shape is stable in intent but may shift before v1.0. Safe for pilots, evaluators, internal tools; wait for v1 before betting critical compliance reporting on it.

What about GDPR / HIPAA / regulated-industry compliance?

The SDK gives you the primitives: per-code pii_in_detail flag forces minimum retention (GDPR minimisation), secret-key redaction runs before emit, audit rows carry actor / target / method / timestamp in a defensible typed shape. Compliance-report generation (HIPAA, SOC2, GMP, ISO 26262, FSSC 22000) is rivet Cloud's paid layer — the SDK feeds it.

What does the SDK cost?

Nothing. Apache-2.0, no seat limits, no per-emit charges, no free-tier gotchas. Paid layer (rivet Cloud) is optional and priced per node / per retention tier. Pricing page ships with v1.

Why not LangSmith or Langfuse for AI-agent audit?

LangSmith locks you to LangChain. Langfuse is close in scope but LLM-ops-first — it lacks the typed 6-anchor audit shape and doesn't cover non-HTTP correlation transports (MQTT, scheduler). rivet coexists — you can ship rows to both; they answer different questions.

What's the performance overhead?

~0.1–0.5 ms per emit() with SQLite WAL. ~1–5 ms with Postgres. Ring buffers use ~8 MB per service at 10 k lines. No background goroutines or threads — all synchronous in the calling thread. High-volume codes can be sampled via short retention class + periodic sweep.

How do I contribute?

Pre-extraction today — the reference implementation lives inside our monorepo. Once the package extracts as a standalone repo (trigger conditions in the design plan), we'll open GitHub issues, a PR flow, a contributor guide, and a governance doc. In the meantime, open issues against the design plan itself.
